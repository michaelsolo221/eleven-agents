# ADR 0007: Scoped Continuous Deployment & Post-Deploy Verification for the Webhook Receiver

## Status

Proposed

## Context

The `server/` microservice (ADR 0006) is deployed to Coolify. Its Coolify app is configured with `git_branch: "main"` and `git_commit_sha: "HEAD"` — consistent with an intent to always run the latest `main` — and Coolify has generated a `manual_webhook_secret_github` for it, which the dashboard likely surfaces as an "Auto Deploy" toggle.

Diagnosed 2026-07-28 while adding the `/version` endpoint (this repo, `server/main.py`) specifically to make "what's actually deployed" answerable:

- `gh api repos/michaelsolo221/eleven-agents/hooks` returns `[]` — **no webhook is registered on the GitHub repo**, despite Coolify holding a secret for one. Coolify generating the secret does not mean the GitHub-side registration happened; that registration is normally handled automatically by Coolify's GitHub App source integration, which this app doesn't use (it uses a plain SSH deploy key, per `docs/server-coolify-deployment.md` §2).
- Coolify's deployment history (`GET /api/v1/deployments/applications/{uuid}`) shows all 9 deployments to date with `is_webhook: false` — every deploy so far has been manually triggered.
- As a direct consequence, production was observed to be a full day and two merged PRs stale (still running the `dad7d98` build after `#50` and `#51` had merged) with nothing surfacing that drift.

Separately: even if the GitHub webhook were correctly registered, a webhook-triggered Coolify deploy is fire-and-forget from GitHub's perspective — the push event returns immediately, the build+deploy happens later on Coolify's server, and nothing reports the result back to GitHub. A webhook alone cannot produce a pass/fail signal on the commit.

### Additional validation (2026-07-28, before finalizing this ADR)

Checked several assumptions directly against the live Coolify API and Coolify's own docs rather than leaving them implicit:

- **Confirmed, no third-party source integration**: the app's `source_id` and `source_type` fields are both `null`, and `watch_paths` is `null` — independently confirms the "no GitHub App source" diagnosis above, and confirms `watch_paths` (a Coolify field intended for exactly this kind of path-scoping) is genuinely unconfigured.
- **Confirmed, deploys are zero-downtime by default**: Coolify uses a "start-before-stop" strategy — a new container starts, must pass its configured health check, and only then is the old container stopped. A failed deploy does **not** take production down; the old container keeps serving. Verified applicable to this app specifically: it requires default container naming (`custom_docker_run_options` is `null` here, so no override) and isn't supported on Docker Compose deployments (this app's `build_pack` is `"dockerfile"`, not compose). This substantially de-risks triggering deploys automatically from CI.
- **Confirmed, no commit-pinning on trigger**: Coolify's `POST /api/v1/deploy` endpoint accepts `uuid`/`tag`, `pr`/`preview`, `docker_image_tag`, and `force` — no `commit` parameter. Triggering a deploy always builds whatever is currently at the tip of the configured branch (`git_commit_sha` is `"HEAD"` on this app, not pinned), not a specific SHA passed by the caller. **This means a post-deploy check that asserts strict equality (`live git_sha == $GITHUB_SHA`) can false-fail**: if a second push lands on `main` while the first push's CI job is still polling, the live SHA will legitimately become a newer commit, not a broken one. The verification design needs to account for this (see Decision, below) rather than assume single-threaded, race-free triggering.
- **Confirmed 2026-07-29, via dashboard (user-checked, not API-visible)**: Coolify's "Include Source Commit in Build" toggle is enabled for this app. The underlying field (`include_source_commit_in_build`) isn't exposed in this instance's `GET /applications/{uuid}` response, so this could only be confirmed by looking at the dashboard directly, not the API.
- **Confirmed 2026-07-29, via Coolify's official docs (`/coollabsio/coolify-docs`)**: `SOURCE_COMMIT` is genuinely the documented build-arg name Coolify injects when that toggle is on — matches what `server/Dockerfile` and `/version` already assume, not a guess.
- **Confirmed 2026-07-29, via the same docs**: `POST /api/v1/deploy`'s response body *is* documented (contrary to the assumption below) — it returns `{"deployments": [{"message", "resource_uuid", "deployment_uuid"}]}`. A caller can read the triggered deployment's UUID directly from the trigger response instead of inferring it by matching timestamps against the deployments list. The verification script should be updated to do this — seeded a real, not just theoretical, mis-attribution risk under overlapping pushes (see Decision, point 2).
- **Confirmed 2026-07-29, via the same docs**: Coolify API tokens are scoped by **team + permission type** (`read`, `read:sensitive`, `write`, `deploy`, `root`), not by individual resource/application. There is no way to create a token that only works against `eleven-agents-webhook` specifically — a `deploy`-permission token can trigger deploys of anything in the same team. Narrows *what* the token can do relative to a broad personal token (no `write`/`read:sensitive`/`root`), but not *which app* it applies to. The Next Steps and Consequences sections below have been corrected to say "permission-scoped," not "resource-scoped."
- **Found 2026-07-29, only by actually running the script (not from any doc)**: Coolify Cloud's edge blocks Python's default `urllib` User-Agent (`Python-urllib/x.y`) with a bare 403, on every endpoint, regardless of token validity or permissions — confirmed by isolating it (same token, same URL: `curl` got 200, bare `urllib.request` got 403, `urllib.request` with an explicit `User-Agent` header got 200). Nothing in Coolify's docs mentions this; without live testing it would have looked like a permissions problem and sent debugging in the wrong direction. Without an explicit `User-Agent` header, this script would 403 on every single CI run from day one, in a way that would have been easy to misdiagnose as a bad token. Fixed by setting `User-Agent: eleven-agents-ci/1.0` on every request the script makes.

## Decision

1. **Scope deploys to `server/` changes only, via a path check inside the CI job.** `main` also carries ElevenLabs agent-config and docs changes unrelated to this service; deploying on every push to `main` would rebuild/restart the container for irrelevant commits. Coolify's `watch_paths` field is *not* a usable alternative here despite superficially looking like one — it only filters webhook-triggered deploys, and this design deliberately doesn't use Coolify's webhook (see below), so it would simply never be consulted.

2. **CI owns the deploy trigger and the feedback loop, not Coolify's webhook.** Add a job to `.github/workflows/agents.yml`, gated `if: github.ref == 'refs/heads/main' && github.event_name == 'push'` (same shape as the existing `push`/`test` jobs, but placed to run in **parallel** with them, only depending on `validate` — it deploys a completely separate system from the ElevenLabs agent push/test chain and shouldn't block on or be blocked by it), that:
   - Checks whether the push touched `server/**`; skips the rest if not (mirrors the `pr-test`-runs-on-unrelated-PRs waste already flagged and worth avoiding here too).
   - `POST`s to Coolify's `/api/v1/deploy?uuid=...` (already documented in `docs/server-coolify-deployment.md` §4) and reads the `deployment_uuid` directly out of that response's `deployments[]` array — **not** by matching timestamps against the deployments list, which was this ADR's original plan until the Additional Validation update above found the response body is actually documented. Timestamp-matching has two real failure modes the `deployment_uuid` approach avoids: clock skew between the GitHub Actions runner and Coolify's server, and misattributing a *different*, overlapping push's deployment to this job when two pushes to `main` land close together (the same overlapping-push scenario the ancestor-check below exists to handle).
   - Polls Coolify's deployment-status endpoint (`GET /deployments/{deployment_uuid}`) until `finished`/`failed`, under an explicit bounded timeout (both a step-level poll cap and a job-level `timeout-minutes:`, matching the existing `pr-test` job's pattern) — an unbounded poll risks a hung CI job if a Coolify deployment stalls. The timeout should budget for the possibility that a prior deploy is still running and this one is queued behind it, not just this deploy's own build+deploy duration.
   - Curls the live `/version` endpoint **with a few retries**, not a single shot — during the start-before-stop handoff window there's a brief period where either the old or new container could plausibly answer, so a single curl right after "finished" status is a plausible source of flakiness.
   - Asserts the returned `git_sha` is the triggering commit **or a later one reachable from it** (e.g. `git merge-base --is-ancestor $GITHUB_SHA <reported_sha>`), not strict equality — per the validated finding above that Coolify's deploy API can't be pinned to a specific commit, so a legitimate newer deploy landing mid-poll must not be reported as a failure. This requires the job's checkout step to use `fetch-depth: 0` (full history) — `actions/checkout@v4`'s default `fetch-depth: 1` won't have the later commit's object locally, so `--is-ancestor` would fail closed even in the legitimate case this check exists to allow.
   - Fails the job — and therefore shows a red check on the commit — only if the deploy itself fails, times out, or the live SHA is neither the triggering commit nor a descendant of it.

   This mirrors the pattern already established for the ElevenLabs side of this repo: push, then a verification step (`verify-live-tools.py`) confirms live state actually matches what was pushed. Same shape, applied to Coolify, adapted for the fact that Coolify's trigger can't be pinned to a commit the way the ElevenLabs CLI push can.

3. **Leave the GitHub-side webhook unregistered.** Since CI is triggering the deploy directly via the API, there's no need to fix the broken webhook wiring — it would be a redundant, worse-feedback path to the same outcome.

## Consequences

- Closes the drift gap that let production silently sit a day and two merges behind: a broken or mismatched deploy now fails visibly in GitHub Actions instead of failing silently.
- Coolify's dashboard "Auto Deploy" toggle becomes misleading if left on with no registered webhook — should be turned off to avoid implying a deploy path that doesn't exist, now that CI is the actual trigger.
- Requires a Coolify API token in GitHub Actions secrets. **Done 2026-07-29**: created a new token (permissions: `deploy` + `read`, not `write`/`read:sensitive`/`root`) and added it as the `COOLIFY_TOKEN` repo secret, replacing the plan to reuse the broad personal-account token used in local/manual use. Per the Additional Validation finding above, Coolify tokens are scoped by team + permission type, not by individual application — so this token is narrower in *what* it can do (can't modify config, read secrets, or bypass checks) but not restricted to *only* `eleven-agents-webhook`; it can trigger/read deploys for anything else sharing that Coolify team. Still a meaningful improvement over the personal token, just not the strict per-resource isolation originally hoped for.
- Requires `git_sha` to actually populate on deploy, which depends on Coolify's "Include Source Commit in Build" toggle being enabled (documented in `docs/server-coolify-deployment.md` §5, added alongside the `/version` endpoint) — **confirmed enabled 2026-07-29** (see Additional Validation above), no longer an open item.
- Because Coolify's deploy trigger can't be pinned to a commit, the post-deploy check is necessarily "a deploy of this commit-or-later succeeded," not "exactly this commit is live." Acceptable for this service's low traffic/low concurrency profile, but worth remembering if that assumption ever stops holding (e.g. if pushes to `main` become frequent enough for overlapping deploys to be common).
