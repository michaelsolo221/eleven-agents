# Claims Supervisor as a separate registered Agent, not a workflow node

We needed a deterministic gate between the Claims Officer collecting claim fields and the call actually ending, to stop the officer from hallucinating completeness and ending the call (or believing it had lodged a claim) with required fields missing.

The first attempt kept a single Agent ("Claims Lodgement Officer") and modeled the officer and supervisor as two `override_agent` workflow nodes, connected by an LLM-conditioned edge (`officer_node` → `supervisor_node`). This was verified, empirically, not to work: across repeated live `simulate-conversation` calls, the edge never actually transitioned the conversation into the supervisor node, even once the officer had genuinely collected every required field and called the intended handoff tool. The pattern held regardless of prompt wording, `entry_behavior` settings, or edge condition wording. The documented examples of LLM-conditioned edges in the ElevenLabs API only ever show them attached to `start`/`entry` nodes or to dedicated tool-dispatch nodes — never directly between two long-running conversational `override_agent` persona nodes, which is the shape we needed. We could not get this shape to work reliably.

We switched to two separate registered Agents — "Claims Lodgement Officer" and "Claims Lodgement Supervisor" — connected by the `transfer_to_agent` system tool, which is a mature, extensively documented, first-class ElevenLabs mechanism (used elsewhere for CCaaS integrations, orchestrator-agent patterns, etc.) rather than the newer workflow-node graph feature. This is a real trade-off, not a strict improvement: `transfer_to_agent` is still triggered by the officer's own LLM judgment (the same class of risk as before — a hallucinated "I'm done" belief can still fire the transfer early), so it is not more deterministic in principle. It works in practice, though, and unlocked something the workflow-node design could not: the Supervisor now has its own agent-level `end_call` while the Officer never had a working way to be blocked from ending the call on its own persona-node — because a node-level `built_in_tools` override was silently rejected by the CLI's SDK, whereas each registered Agent's own top-level `built_in_tools` is a normal, confirmed-working field. The officer keeps `end_call` regardless (see below), so this benefit is smaller in practice than we first expected, but the transfer mechanism itself does now demonstrably work end-to-end, which the workflow-node edge did not.

## Officer keeps `end_call`

The PRD (issue #3) requires the officer to end the call directly in several non-claim-completion cases: emergency redirect (story 18), unresponsive caller (21–22), WhatsApp session timeout (25), and wrong number (26). Stripping `end_call` from the officer entirely — the original plan, on the theory that it would force every call-ending path through the Supervisor — would have broken all four of those. `end_call` stays on the Officer; the constraint is enforced by prompt instruction (never call `end_call` to conclude a completed claim; only for the four cases above) plus the completeness guardrail as a backstop, not by removing the tool.

## Layered defense, since no single layer is airtight

1. Officer's own completeness self-check, before deciding to transfer (can be wrong).
2. Officer's prompt instruction to transfer rather than end the call on claim completion (can be ignored or fired early — observed in testing, see below).
3. Supervisor's independent re-read of the actual transcript before confirming lodgement (can also be wrong — observed failing in the offline test-mode harness, though not in live `simulate-conversation` runs; see the divergence note in the PR).
4. A custom guardrail (`Claim completeness before closing`), evaluated on every response, that blocks and forces a retry of any response that ends the call or declares the claim lodged while a required field is genuinely absent from the transcript.

None of layers 1–3 are individually reliable; the guardrail is the only mechanical, code-adjacent check in the stack. This is a known, accepted limitation, not a solved problem — see the PR description for the specific test evidence and what's still open.

## CLI push bug

`elevenlabs agents push` (CLI 0.5.4 and 0.5.5, the latest at time of writing) was observed to silently drop certain tool entries — inline webhook tool definitions and `transfer_to_agent` — from the request it sends, with no warning, while reporting success. A direct API `PATCH` with the identical payload persists correctly, so the bug is in the CLI's request serialization, not the API. `scripts/verify-live-tools.py` was added to the CI `push` job specifically to catch this: it re-fetches each agent from the live API after push and fails the build if a locally-declared tool didn't make it across, rather than letting this fail silently in production again.
